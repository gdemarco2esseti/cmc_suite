# Release notes - CMC suite refactor 2026-10

Branch `refactor/suite-2026-10`. Upgrades databases at `19.0.1.0.0` / `19.0.1.1.0`.
Read the whole page before upgrading: part of the history cannot be converted
automatically and the migration tells you so in the log instead.

## 1. Sign convention (AD-005)

**Before:** a manual cost entry (Cost Entries screen) was stored as a POSITIVE analytic amount, while
costs coming from documents (vendor bills, timesheets, MO labour) were already negative, Odoo's way.

**Now:** a cost is a NEGATIVE analytic amount everywhere, the Odoo one. The Cost Entry form still
takes the cost as a positive figure (`cmc_cost_amount`) and stores it negative. The cost engines
(`_cmc_cost_groups`, closing, costing, CVR, ABC...) read costs as the opposite of the amount.

### What the migration does (`cmc_base` 19.0.1.2.0, post-migrate)
- Flips to negative the **manually classified** cost entries: positive amount, classified (behavior, cost
  element or activity), no document behind them (no financial account, project, employee, journal item,
  MO move, stock valuation), not excluded, and either flagged manual or carrying neither behavior nor
  element.
- Refreshes every stored capacity analysis figure.

### What it does NOT do
- It does **not** flip lines classified by a classification **rule**: they may be imported revenues
  (positive on purpose). Under the new sign a positive amount on such a line *reduces* cost.
- It does **not** flip lines born from a document: they already had Odoo's sign.
- It cannot tell an old-convention reversal (negative manual entry) from a genuine cost already negative.
- It does **not** recompute concluded runs.

### Warnings to read in the log (logger `odoo.upgrade.cmc_base.19.0.1.2.0.post-migrate`)
| Message | What to do |
|---|---|
| `positive classified entries without a document classified by a rule: under the new sign a positive amount reduces cost - verify by hand` (count + ids, first 50) | Open the ids: a revenue stays positive, a cost must be made negative by hand. |
| `classified entries without a document already have a negative amount ... verify by hand` | Possible old reversals: check each one. |
| `<run table> <id> (<name>, company <n>) concluded and computed on the old sign: reset to draft and recompute` | One line per concluded closing, costing, actual-mode CVR analysis and ABC run whose period contains a flipped or ambiguous line. See section 6. |

## 2. Closing runs require a period

`cmc.closing.run` has mandatory `date_from` / `date_to`; a costing run must sit inside the period of its
closing. Migrations: `cmc_base` 19.0.1.1.0 gives undated closings the span they aggregated;
`cmc_full_costing` 19.0.1.1.0 gives an undated costing run the period of its closing run
(without it the NOT NULL constraint could not be created and Odoo logged schema errors).

## 3. Manual classifications live per cost center

A manual override is stored in `cmc.manual.classification`, keyed by (journal item, cost center), and
survives draft / re-post. It is no longer a column of the journal item.

`cmc_account` 19.0.1.2.0 migration:
- carries every manual analytic line to the new model (one record per journal item and center);
- **also carries the overrides of journal items in draft**, which exist only on the old
  `account_move_line.cmc_*` columns (draft deletes the analytic lines): one record per cost center of
  the item's analytic distribution (a multi-plan key `"id1,id2"` counts every center of the key;
  with no center in the key, every account of the key);
- then drops the four old columns.

Log to read: `manual journal item(s) without analytic distribution, the override is lost: ids ...` - those
overrides cannot be reconstructed, classify them again by hand.

## 4. MRP labour twin

The analytic line generated by the labour journal entry of a manufacturing order duplicates the
workcenter line: it is now excluded from the cost base (`cmc_excluded`), so labour counts once.
`cmc_mrp` 19.0.1.1.0 migration backfills the history: for every entry linked to
`mrp_workcenter_productivity.account_move_line_id` all journal items are flagged excluded and their
analytic lines are excluded and unclassified; capacity figures are recomputed. The log reports how
many analytic lines were excluded (`cmc_mrp: N historical labour twin analytic line(s) excluded`).
Cost figures of past periods drop accordingly: recompute the runs (section 6).

## 5. Bridge `cmc_timesheet_grid` (new)

Enterprise-only (OEEL-1), `auto_install` when `timesheet_grid` and `cmc_hr_timesheet` are present
(on a fresh install; an update does not install a new module on an existing database).
It lets CMC controllers classify **validated** timesheets, through the same single classification
gate used by every other CMC controller. Nothing to migrate. On an existing database with Enterprise, install it explicitly
(`-i cmc_timesheet_grid`).

## 6. One lifecycle for every run (AD-001, AD-002)

Closing, full costing, ABC, joint costs and TDABC runs share `cmc.run.mixin`:

- **A computed run is locked.** Its header inputs (period, method, company, joint cost, closing,
  base, products) and its input lines cannot change; the form shows them read-only. Writes over
  RPC, including as superuser, raise an error.
- **Its results are locked too.** Result rows are written only by *Compute* and deleted only by
  *Reset to Draft*; nobody can add, change or delete them by hand, on a computed run or on a draft one.
- **Compute starts from draft only.** To recompute: *Reset to Draft* (it **deletes the results**,
  after a confirmation), change what is needed, *Compute*.
- **A closing run cannot be reset or deleted while a computed costing run reads it.** Reset the
  costing runs first (the error names them). No cascade.
- Behaviour changes: joint runs no longer reopen themselves when a line changes (the change is
  refused); a full-costing reset now deletes its results; closing and TDABC runs gained the reset;
  a cost center used by a computed closing cannot be deleted.

`cmc_full_costing` 19.0.1.2.0 post-migrate deletes the stale results of draft costing runs (the
old reset kept them). Log: `Removed N stale results of draft costing runs.`

## 7. Bridges declare profiles; a bridge withdraws what it set

The operational bridges (timesheet MOD, MRP labour) declare a profile (`_cmc_bridge_profiles()`);
one engine in `cmc_account` applies them. The new field `cmc_bridge_source` records which profile
classified a line and which fields it filled. When the line stops matching (hours moved to an
auxiliary or period center, hours zeroed, an MO line that is not labour) those fields are cleared
and the classification rules decide again. Values set by a rule, by hand or by MRP adoption are kept.

Migrations `cmc_hr_timesheet` / `cmc_mrp` 19.0.1.2.0 tag the lines already carrying the bridge
values (log: `Tagged N lines classified by the ... bridge`). **The history is corrected on first
touch, not during the upgrade:** a past line that no longer matches its profile keeps its MOD
classification until something re-classifies it (a trigger field written, *Re-apply
Classification Rules*). Re-applying rules on a closed period can therefore change it: recompute
the runs of that period afterwards.

## 8. Other changes

- The Unclassified Cost Lines queue opens on its own list (cost amount, editable classification
  columns), also with `hr_timesheet` installed.
- Engine internals split into steps; one `spread()` for every proportional split. Figures are the
  same; a residual cent may land on a different product only in exact ties.
- `cmc.cvr.analysis.leverage_impact()` removed (unused).
- A costing run with a period or figurative cost but no driver consumption now stops with an
  error instead of silently leaving that cost out of every product.
- Computed figures no longer depend on who presses *Compute*: the engines read the analytic
  lines of the run's company whatever the user's own record rules (e.g. "own timesheets only").
- Users can read, not write, `cmc.manual.classification` directly; classifying a line still
  works as before (the system writes the override).
- Master data used by computed results (products, partners, TDABC activities and resources, cost
  centers of a closing) cannot be deleted while those results exist.
- Italian translations regenerated.
- Record rules are no longer `noupdate`: a pre-migrate in each module clears the flag on
  installed databases, so future fixes to a rule's domain reach them.
- MRP labour twins rebuilt by core (repost, reversal) are no longer stored as manual
  classifications.

## 9. Upgrade procedure

1. **Backup** the database (and filestore) first. Rehearse on a copy.
2. Update **all** CMC modules together, not only the ones you depend on directly:
   ```
   odoo-bin -d <db> -u cmc_base,cmc_account,cmc_hr_timesheet,cmc_mrp,cmc_full_costing,cmc_direct_costing,cmc_abc,cmc_joint_costs,cmc_tdabc,cmc_suite --stop-after-init --log-level=info
   ```
   (add `cmc_timesheet_grid` where Enterprise is available). Migrations of one module read the
   models of the others.
3. Read the log: `grep -E "upgrade\.cmc|cmc_.*migrate|WARNING|ERROR"`. Every warning in sections 1
   and 3 needs a decision.
4. For each run listed as computed on the old sign, and for closings whose labour changed with the
   MRP backfill:
   1. reset to draft the **costing runs** and the ABC runs of the period;
   2. reset to draft the **closing runs** (refused while a computed costing reads them);
   3. compute the closing runs, then the costing runs and the ABC runs;
   4. press *Recompute* on the actual-mode CVR analyses (they have no draft/computed state).
5. Check the Unclassified queue and the Cost Entries screen for the lines flagged by the warnings.

Rehearsed on a copy of the `cmc_all` demo (2026-10-09): upgrade from 19.0.1.0.0 without errors,
15 runs listed, 120 timesheet lines tagged, reset + recompute of all 15 completed.
